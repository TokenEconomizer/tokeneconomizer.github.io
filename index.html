In short

Coding agents such as Claude Code, Codex, and GitHub Copilot CLI are usually evaluated one task at a time, but developers use them on the same codebase task after task. In that setting, much of what an agent pays for recurs: it rediscovers the same facts about the repository, carries the descriptions of tools it never uses, and keeps retrying when it is stuck.

TokenEconomizer is a controller that sits outside the agent. After every task in a repository, it learns from what the agent did and adjusts three things for the next task: which short facts about the repository to tell the agent, which tools to load, and when to step in on a failure loop. It changes neither the model nor the agent's code.

On 277 SWE-Bench tasks, it lowers average cost by 18.4–30.9% across the five agent–model settings we evaluated, with comparable task success. The savings also carry over to web development and security auditing.

1 Motivation

Coding agents are built for task success, not token efficiency

Claude Code, Codex, and GitHub Copilot CLI are designed to complete tasks, and their growing capability comes at a substantial token cost. On every turn, an agent is billed for its whole context: the system instructions, the descriptions of every tool, and everything that has happened in the task so far. Caching makes this replayed context cheaper, but it is still paid for on every turn.

Developers also return to the same codebase task after task, yet each task starts from scratch. What one task learns about the repository, such as how to run its tests, is rediscovered and paid for again in the next.

Three kinds of recurring waste

We profiled 60 SWE-Bench tasks run by an unmodified agent. Three patterns stand out, and TokenEconomizer has one strategy for each.

1Rediscovering the same facts

Agents keep working out how to run the tests or where the code lives. After five or more tasks in a repository, 30% of tool calls repeat an action from an earlier task.

Micro-skill injection tells the agent short facts about the repository, verified on every later task.

2Paying for unused tools

Every turn bills the descriptions of 23 tools, but 16 of them are never called, in any repository.

Tool pruning unloads tools the repository does not need, and brings them back if it does.

3Getting stuck on failures

The 17% of tasks that fail take 32% of the spend, and how much longer failing runs last varies by repository.

Failure-loop intervention spots unproductive loops, redirects the agent, and stops it if the loop persists.

Why not a fixed strategy? Fixed strategies from popular open-source tools, such as RTK, Serena, and RepoMap, apply one configuration everywhere, and in our profile each one lowers cost in some repositories but raises it in others. TokenEconomizer instead learns what to do in each repository from that repository's own completed tasks.

2 Method

How TokenEconomizer works

TokenEconomizer treats the agent as a black box. It acts only through what the harness already exposes, namely the instruction prefix, the loaded tools, and the live event stream, and never changes model weights or agent-loop code. Tasks \(\tau_1,\ldots,\tau_n\) in an environment arrive in order. Before task \(\tau_i\), the controller reads the repository state \(S_{i-1}\) distilled from the tasks completed so far and sets three policies:

\[(\Delta P_i,\ \mathcal{U}_i,\ B_i) \;=\; \mathcal{C}(\tau_i,\ S_{i-1})\]

\(\Delta P_i\): the micro-skills activated for this task  ·  \(\mathcal{U}_i\): the tools loaded  ·  \(B_i\): the turn budget that calibrates the failure-loop guard. The controller can always leave the default configuration in place, and its own model calls are charged to the task that triggers them.

1

Micro-skill injection

Knowledge · between tasks

  1. Propose

    Every \(T=5\) tasks, an LLM proposer turns digests of recent traces into one-line facts about the repository, each with executable detectors.

  2. Check every trace

    After each task, the detectors test whether the trace confirmed or contradicted each fact, and whether the task needed it. No model call is involved.

  3. Inject selectively

    A fact enters the prompt only after \(n=3\) tasks with non-overlapping edits confirm it, and only while its need rate, the share of tasks exercising it that needed it, stays at or above \(\rho=0.4\).

  4. Retire on contradiction

    Support decays older evidence by a factor \(\gamma=0.8\) per task, and one contradiction counts as \(\lambda=5\) confirmations. Once the support drops below zero, the fact is retired for good.

2

Tool pruning

Interface · before each task

  1. Protect the core

    Tools for shell execution and for reading, writing, and editing files are always kept.

  2. Mask on evidence

    A tool is masked once \(k=3\) consecutive tasks have left it uncalled.

  3. Mask on relevance

    An LLM judge reviews each never-called tool against the task description, with links to the repository's pull requests, issues, commits, and files masked out.

  4. Re-audit

    Every \(R=5\) tasks, the full catalog is restored, and a tool called during a re-audit is never masked again.

3

Failure-loop intervention

Control · during the rollout

  1. Learn a turn budget

    The \(p\)-th percentile (\(p=90\)) of the turn counts of the repository's successful runs so far, times a margin \(\beta=1.25\):

    \[B_i=\beta\cdot Q_p\bigl(\{|\xi_j| : j<i,\ y_j=1\}\bigr)\]

  2. Watch cheaply

    After each tool call, rule-based checks look for repeated failures, dense errors, or a run past \(B_i\). No model call is involved.

  3. Judge, then redirect

    An LLM judge reads a digest of recent actions. If it finds the agent stuck with confidence at least \(c=0.7\), the agent is redirected with a summary of what it has tried; if the loop recurs, the run ends.

  4. Backstop

    At \(\kappa B_i\) turns, with \(\kappa=2.5\), a forced stop applies when edit churn, dense errors, and a repeated failure occur together.

The values given are the settings used in our experiments. The same values serve every agent, model, and repository; they were fixed in development runs before the main experiments, and the other benchmarks change only what their task streams require. Each one can be changed to suit a deployment: for example, a smaller \(n\) or \(k\), or a smaller \(\beta\) or \(\kappa\), acts sooner and saves more, at a higher risk of a wrong decision.

3 Results on SWE-Bench

Consistent savings across the agents, models, and repositories we evaluated

Five agent–model settings across Claude Code, Codex, and GitHub Copilot CLI run the same 277 SWE-Bench tasks from 6 repositories, in each repository's chronological order. TokenEconomizer lowers mean cost by 18.4–30.9% and improves Pass@1 in four of the five settings. Cost is cache-aware and charges every controller call to the task that triggered it.

      4 Generalization

      Savings carry over to web development and security auditing

      Web-Bench tasks build on one continuous project and inherit earlier workspace changes. In the security benchmarks, each task targets a different repository under a fixed audit prompt, so repository-specific micro-skills are switched off and the other two meta-strategies run alone.
