1 Motivation

Coding agents are built for task success, not token efficiency

Every turn re-bills the agent's whole context: its instructions, every tool description, and the task so far. Developers use agents on the same codebase over many tasks, yet efficiency is optimized one task at a time, so knowledge about the environment is often paid for again in later tasks.

Three kinds of recurring waste

From 60 profiled SWE-Bench runs of an unmodified agent, each matched by one strategy:

1Rediscovering the same facts

30% of tool calls repeat an earlier task's action once a repository has five or more tasks behind it.

→ Micro-skill injection

2Paying for unused tools

16 of the 23 tool descriptions billed on every turn are never called.

→ Tool pruning

3Getting stuck on failures

The 17% of tasks that fail take 32% of the spend.

→ Failure-loop intervention

Why not a fixed strategy? RTK, Serena, and RepoMap each lower cost in some repositories and raise it in others, so TokenEconomizer learns what to do in each repository instead.

2 Method

How TokenEconomizer works

An external controller that acts only through what the agent already exposes. After every task, it updates three policies for the next one.

Step by step: what each meta-strategy does, and its settingsexpand

TokenEconomizer treats the agent as a black box. It acts only through what the harness already exposes, namely the instruction prefix, the loaded tools, and the live event stream, and never changes model weights or agent-loop code. Tasks \(\tau_1,\ldots,\tau_n\) in an environment arrive in order. Before task \(\tau_i\), the controller reads the repository state \(S_{i-1}\) distilled from the tasks completed so far and sets three policies:

\[(\Delta P_i,\ \mathcal{U}_i,\ B_i) \;=\; \mathcal{C}(\tau_i,\ S_{i-1})\]

\(\Delta P_i\): the micro-skills activated for this task  ·  \(\mathcal{U}_i\): the tools loaded  ·  \(B_i\): the turn budget that calibrates the failure-loop guard. The controller can always leave the default configuration in place, and its own model calls are charged to the task that triggers them.

1

Micro-skill injection

Knowledge · between tasks

  1. Propose

    Every \(T=5\) tasks, an LLM proposer turns digests of recent traces into one-line facts about the repository, each with executable detectors.

  2. Check every trace

    After each task, the detectors test whether the trace confirmed or contradicted each fact, and whether the task needed it. No model call is involved.

  3. Inject selectively

    A fact enters the prompt only after \(n=3\) tasks with non-overlapping edits confirm it, and only while its need rate, the share of tasks exercising it that needed it, stays at or above \(\rho=0.4\).

  4. Retire on contradiction

    Support decays older evidence by a factor \(\gamma=0.8\) per task, and one contradiction counts as \(\lambda=5\) confirmations. Once the support drops below zero, the fact is retired for good.

2

Tool pruning

Interface · before each task

  1. Protect the core

    Tools for shell execution and for reading, writing, and editing files are always kept.

  2. Mask on evidence

    A tool is masked once \(k=3\) consecutive tasks have left it uncalled.

  3. Mask on relevance

    An LLM judge reviews each never-called tool against the task description, with links to the repository's pull requests, issues, commits, and files masked out.

  4. Re-audit

    Every \(R=5\) tasks, the full catalog is restored, and a tool called during a re-audit is never masked again.

3

Failure-loop intervention

Control · during the rollout

  1. Learn a turn budget

    The \(p\)-th percentile (\(p=90\)) of the turn counts of the repository's successful runs so far, times a margin \(\beta=1.25\):

    \[B_i=\beta\cdot Q_p\bigl(\{|\xi_j| : j<i,\ y_j=1\}\bigr)\]

  2. Watch cheaply

    After each tool call, rule-based checks look for repeated failures, dense errors, or a run past \(B_i\). No model call is involved.

  3. Judge, then redirect

    An LLM judge reads a digest of recent actions. If it finds the agent stuck with confidence at least \(c=0.7\), the agent is redirected with a summary of what it has tried; if the loop recurs, the run ends.

  4. Backstop

    At \(\kappa B_i\) turns, with \(\kappa=2.5\), a forced stop applies when edit churn, dense errors, and a repeated failure occur together.

The values given are the settings used in our experiments. The same values serve every agent, model, and repository; they were fixed in development runs before the main experiments, and the other benchmarks change only what their task streams require. Each one can be changed to suit a deployment: for example, a smaller \(n\) or \(k\), or a smaller \(\beta\) or \(\kappa\), acts sooner and saves more, at a higher risk of a wrong decision.
