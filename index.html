Abstract

Advances in frontier coding agents have sharply increased the token costs of AI-assisted software engineering. Their token efficiency is typically evaluated on isolated tasks, whereas real-world developers use them to continuously build, update, and maintain large-scale projects. This mismatch motivates us to evaluate agents over sequences of realistic coding tasks, where we find that agents exhibit recurring environment-dependent token costs that existing methods struggle to reduce. To minimize these costs, we introduce TokenEconomizer, an external controller that cuts environment-specific token costs over a sequence of tasks. These cuts come from determining (i) which operational micro-skills to inject, (ii) which persistently irrelevant tools to prune, and (iii) when to intervene in unproductive failure loops. Across Claude Code, Codex, and GitHub Copilot CLI paired with frontier models, TokenEconomizer reduces the average token cost by 18.4–30.9% with comparable task success. Savings hold in every repository under every tested agent–model setting and generalize to diverse domains such as sequential web development and security auditing, where costs fall by 6.4–21.2% depending on task structure. Our work establishes adaptive black-box cost control as a promising direction for reducing token costs of coding agents in realistic settings.

1 Motivation

Coding agents keep paying for the same work

On every turn, a coding agent is billed for its whole context: the system instructions, the descriptions of every tool, and everything that has happened in the task so far. Caching makes this replayed context cheaper, but it is still paid for on every turn.

Developers also return to the same codebase task after task, yet each task starts from scratch. What one task learns about the repository, such as how to run its tests, is rediscovered and paid for again in the next.

Three kinds of recurring waste

We profiled 60 SWE-Bench tasks run by an unmodified agent. Three patterns stand out, and TokenEconomizer has one strategy for each.

1Rediscovering the same facts

Agents keep working out how to run the tests or where the code lives. After five or more tasks in a repository, 30% of tool calls repeat an action from an earlier task.

Micro-skill injection tells the agent short facts about the repository, verified on every later task.

2Paying for unused tools

Every turn bills the descriptions of 23 tools, but 16 of them are never called, in any repository.

Tool pruning unloads tools the repository does not need, and brings them back if it does.

3Getting stuck on failures

The 17% of tasks that fail take 32% of the spend, and how much longer failing runs last varies by repository.

Failure-loop intervention spots unproductive loops, redirects the agent, and stops it if the loop persists.

Why not a fixed plugin? Popular plugins such as RTK, Serena, and RepoMap apply one configuration everywhere, and each one lowers cost in some repositories but raises it in others. TokenEconomizer instead learns what to do in each repository from that repository's own completed tasks.

2 Method

One controller, three meta-strategies, a policy learned for each environment

TokenEconomizer treats the agent as a black box. It acts only through what the harness already exposes, namely the instruction prefix, the loaded tools, and the live event stream, and never changes model weights or agent-loop code. Tasks \(\tau_1,\ldots,\tau_n\) in an environment arrive in order. Before task \(\tau_i\), the controller reads the repository state \(S_{i-1}\) distilled from the tasks completed so far and sets three policies:

\[(\Delta P_i,\ \mathcal{U}_i,\ B_i) \;=\; \mathcal{C}(\tau_i,\ S_{i-1})\]

\(\Delta P_i\): the micro-skills activated for this task  ·  \(\mathcal{U}_i\): the tools loaded  ·  \(B_i\): the turn budget that calibrates the failure-loop guard. The controller can always leave the default configuration in place, and its own model calls are charged to the task that triggers them.

1

Micro-skill injection

Knowledge · between tasks

  1. Propose

    Every few tasks, an LLM proposer turns digests of recent traces into one-line facts about the repository, each with executable detectors.

  2. Check every trace

    After each task, the detectors test whether the trace confirmed or contradicted each fact, and whether the task needed it. No model call is involved.

  3. Inject selectively

    A fact enters the prompt only after 3 tasks with non-overlapping edits confirm it, and only while at least 40% of the tasks that exercise it need it.

  4. Retire on contradiction

    Each task that confirms a fact adds support, older evidence decays, and one contradiction counts as \(\lambda=5\) confirmations. Once the support drops below zero, the fact is retired for good.

2

Tool pruning

Interface · before each task

  1. Protect the core

    Tools for shell execution and for reading, writing, and editing files are always kept.

  2. Mask on evidence

    A tool is masked once 3 consecutive tasks have left it uncalled.

  3. Mask on relevance

    An LLM judge reviews each never-called tool against the task description, with links to the repository's pull requests, issues, commits, and files masked out.

  4. Re-audit

    The full catalog is periodically restored, and a tool called during a re-audit is never masked again.

3

Failure-loop intervention

Control · during the rollout

  1. Learn a turn budget

    From the turn counts of the repository's successful runs so far, with a high percentile \(p\) and a margin \(\beta>1\):

    \[B_i=\beta\cdot Q_p\bigl(\{|\xi_j| : j<i,\ y_j=1\}\bigr)\]

  2. Watch cheaply

    After each tool call, rule-based checks look for repeated failures, dense errors, or a run past \(B_i\). No model call is involved.

  3. Judge, then redirect

    An LLM judge reads a digest of recent actions. A confidently stuck agent is redirected with a summary of what it has tried; if the loop recurs, the run ends.

  4. Backstop

    At \(2.5\,B_i\) turns, a forced stop applies when edit churn, dense errors, and a repeated failure occur together.

3 Results on SWE-Bench

Cheaper in every repository, under every agent and model

Five agent–model settings across Claude Code, Codex, and GitHub Copilot CLI run the same 277 SWE-Bench tasks from 6 repositories, in each repository's chronological order, with three seeds. TokenEconomizer lowers mean cost by 18.4–30.9% and improves Pass@1 in four of the five settings. Cost is cache-aware and charges every controller call to the task that triggered it.

      4 Generalization

      Savings carry over to web development and security auditing

      Web-Bench tasks build on one continuous project and inherit earlier workspace changes. In the security benchmarks, each task targets a different repository under a fixed audit prompt, so repository-specific micro-skills are switched off and the other two meta-strategies run alone.
